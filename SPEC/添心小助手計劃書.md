## 2026-05-28 23:42 | 編輯器多點替換匹配錯位導致文檔截斷損毀

### 1. 事件經過
*   **背景**：總監下達修改 `木作工程分析要點.md` 以擴充工藝標準的指令。
*   **起因**：助理使用 `multi_replace_file_content` 工具進行三處非連續性區塊的替換。
*   **問題**：
    1. 第一個替換區塊在寫入時增加了檔案行數，導致後續區塊的預設 `StartLine` 與 `EndLine` 行號發生向下偏移。
    2. 第三個區塊的 `TargetContent` 尾端字符在匹配時因些微格式差異（換行符不一致），導致編輯器發生錯位，誤將「壁板工程」、「電視牆工程」等段落大範圍刪除，且殘留了亂碼控制字元。
*   **結果**：導致 `木作工程分析要點.md` 發生結構損毀與截斷，且出現無法以 `view_file` 讀取（報 MIME type 錯誤）的異常狀態。

### 2. 復原行動
*   **解決方案**：助理立即啟動修復程序，放棄增量式 replace，使用 `write_to_file` 工具開啟 `Overwrite: true` 機制，將先前備份之完整正確 Markdown 內容（包含修補後的全部章節）整檔覆寫回去。
*   **修復結果**：成功。`木作工程分析要點.md` 回歸 100% 健全狀態，且完整注入所有擴充指標。

### 3. 經驗教訓與防範雷區
1.  **避免在行數變動大時使用 multi-replace**：如果一次要修改多處且會造成行數大幅增減，避免在同一次 `multi_replace_file_content` 呼叫中傳入多個區塊，因為編輯器行號會動態漂移。
2.  **優先整檔覆寫**：對於純文字文檔（如 Markdown 資料庫或規格書），若修改幅度較大或涉及重新排版，直接使用 `write_to_file` 整檔覆寫比 `replace` 更為安全可靠。
3.  **Contiguous 逐步替換**：若必須使用 `replace`，應拆分為多次 sequential 單點替換呼叫，每次修改完畢重新 read 確認行號後，再進行下一個點的替換。
